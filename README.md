# Сільпо Навігатор — агент, який веде Гостя до полиці

3D-навігація по залу «Сільпо» на **офіційному MCP**: агент сам збирає контекст магазину
(філія → слот → категорії → товари → акції → кошик), будує схему залу, прокладає маршрут
до потрібного товару й дорогою підказує **Цінотижики**, які лежать по шляху.

Проєкт для хакатону [«Сільпо» AI Factory](https://ai-factory.silpo.ua).

## Проблема Гостя

У великому «Сільпо» 20+ відділів і десятки тисяч SKU. Гість витрачає більшу частину часу
не на вибір, а на **пошук фізичного місця товару**: ходить колами, перепитує персонал,
пропускає акції, бо не знає, що вони на його шляху. Знайти товар в застосунку легко —
знайти його в залі досі ні.

Агент відповідає на питання, яке не закриває ні сайт, ні застосунок:
**«де саме це лежить у цьому магазині і що вигідне мені трапиться дорогою?»**

## Що робить агент (агентний сценарій, а не генерація тексту)

Один запит Гостя «молоко» запускає послідовність дій через tools MCP:

1. `silpo_list_branches` — знаходить магазин, який обрав Гість (378 філій, пошук з нормалізацією «вулиця/вул.»).
2. `silpo_get_time_slots` — валідує слот, щоб отримати контекст кошика (`branchId` + `deliveryType` + `timeslot`).
3. `silpo_get_categories_tree` + `silpo_get_categories` — витягує реальні відділи магазину та їхні підкатегорії.
4. Генерує планіровку залу під ці відділи й розставляє стелажі та холодильники.
5. `silpo_find_products_batch` — шукає товар у каталозі саме цієї філії.
6. Матчить товар у відділ, будує маршрут від входу через проходи до полиці.
7. `silpo_get_promotions` + `silpo_get_products` — бере «Цінотижики» і залишає лише ті, що лежать **на маршруті** (геометрія: відстань від полиці до траєкторії < 5 м).
8. `silpo_add_or_update_cart_products` — додає вибране у справжній кошик Гостя, з яким він іде на касу або оформлює доставку.

Список покупок обробляється так само, але маршрут будується через усі відділи (nearest-neighbour
по коридорах) і завершується на касах.

## Використані tools MCP «Сільпо»

| Область | Tools |
| --- | --- |
| Магазини й доставка | `silpo_list_branches`, `silpo_get_time_slots` |
| Каталог | `silpo_get_categories`, `silpo_get_categories_tree`, `silpo_get_promotions`, `silpo_get_products` |
| Пошук товарів | `silpo_find_products_batch` |
| Кошик | `silpo_get_my_shopping_cart`, `silpo_create_shopping_cart`, `silpo_get_shopping_cart_by_id`, `silpo_add_or_update_cart_products`, `silpo_remove_cart_products` |
| Гість | `silpo_get_my_profile`, `silpo_get_loyalty_info` |

Авторизація — **OAuth 2.1 + PKCE з Dynamic Client Registration**, як описано в документації MCP.
Застосунок ніколи не бачить Silpo JWT: у cookie-сесії живе лише MCP-токен гостя.
Жодних неофіційних API або скрапінгу — усі дані йдуть через `https://mcp.silpo.ua/mcp`.

## Чому планіровка генерується

Схем розстановки стелажів у MCP немає — це дані, які є тільки в мережі. Тому навігатор
**генерує правдоподібний зал** із seed (для одного магазину схема стабільна, кнопка 🎲 дає іншу):
периметр під фреш і холодильники, гондоли в центрі, головний прохід, каси біля виходу.
Кількість гондол розраховується під реальну кількість відділів філії, тому кожен відділ
із MCP отримує своє місце.

Коли мережа підключить реальні планограми, генератор замінюється одним JSON-ом на магазин —
решта пайплайну (матчинг товару у відділ, маршрут, акції по дорозі) не змінюється.

## Інтеграція

- **Мобільний застосунок «Сільпо»** — WebView-екран «Знайти в магазині» у картці товару та в кошику: маршрут відкривається на місці, кошик спільний, бо це той самий MCP-кошик Гостя.
- **Термінал у залі** — той самий інтерфейс на екрані біля входу.
- **Окремий PWA** — `manifest.webmanifest`, safe-area, standalone-режим, теми з палітри AI Factory.
- **Категорійний менеджмент** — зворотний бік продукту: видно, які товари шукають у залі й які акції реально попадають на маршрути.

## Валідація цінності

Що можна виміряти на пілоті в одному магазині:

- **Час до товару**: A/B — Гість із навігатором проти Гостя без нього (секундомір на 5 типових товарах).
- **Питання до персоналу**: підрахунок звернень «де у вас…» до і під час пілота.
- **Конверсія підказок**: частка `on-the-way` акцій, доданих у кошик (метрика вже є в API — `discountPercent`, `detourMeters`).
- **Середній чек**: приріст за рахунок Цінотижиків, які Гість побачив на маршруті, а не пропустив.
- **Якість матчингу**: частка товарів, для яких відділ визначено правильно (на 18 типових запитах у київській філії — 18/18).

Наступний крок масштабування: планограми від мережі → точність до конкретної полиці,
позиціювання по Wi-Fi/BLE → «ви тут» у реальному часі.

## Локальний запуск

```bash
npm install
npm start        # http://localhost:3000
```

Далі — кнопка «Увійти через Сільпо»: відкриється `auth.silpo.ua`, після входу навігатор
працює від імені гостя. Токен зберігається у підписаному cookie цього браузера.

Змінні середовища:

| Змінна | Призначення |
| --- | --- |
| `PORT` | порт локального сервера (типово 3000) |
| `PUBLIC_URL` | зовнішній URL для `redirect_uri` OAuth (потрібен при деплої або тесті з телефона) |
| `SESSION_SECRET` | секрет для підпису cookie-сесії |

## Деплой

Проєкт stateless — сесія гостя живе в cookie, тому працює як звичайний Node-сервер і як
serverless на Vercel (`api/index.js` + `vercel.json`). Для Vercel достатньо задати
`SESSION_SECRET`; `PUBLIC_URL` підставляється з домену автоматично.

## Структура

```
server/
  app.js       — маршрути API, cookie-сесія на запит
  mcp.js       — підключення до MCP «Сільпо», пул клієнтів, OAuth-потік
  session.js   — підписані cookie-сесії та OAuthClientProvider
  silpo.js     — доменна логіка: магазини, відділи, пошук, акції, кошик
  layout.js    — генератор планіровки залу, матчинг товару у відділ, маршрути
public/
  index.html   — мобільний інтерфейс у палітрі AI Factory
  js/store3d.js — 3D-зал на Three.js: стелажі, холодильники, маршрут
api/index.js   — точка входу для Vercel
```
